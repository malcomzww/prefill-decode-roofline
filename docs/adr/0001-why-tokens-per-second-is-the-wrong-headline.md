# ADR 0001: Why tokens/sec is the wrong headline metric

- **Status:** Accepted
- **Date:** 2026-08-25
- **Context:** measurements in `results/roofline.md`, generated by
  `scripts/generate_results.py`

## Context

Serving benchmarks are usually reported as a single tokens/sec figure. It is
the number that appears in launch posts, in vendor comparisons, and in the
first slide of most inference decks.

The measurements in this repo make that figure hard to defend as a *headline*.
Inference is two phases with different bottlenecks, and tokens/sec averages
across them:

| phase | arithmetic intensity (batch 1, S=1024) | bound by |
|---|---|---|
| prefill | ~1024 FLOP/byte | compute |
| decode | ~1 FLOP/byte | memory bandwidth |

The gap is about three orders of magnitude, and it is structural rather than
incidental. Prefill loads each weight once and reuses it across every prompt
token. Decode loads the entire weight set to produce a single token: two FLOPs
for every two-byte weight, an arithmetic intensity of ~1 by construction.

Two measured facts from this machine sharpen the point:

1. Sustained DRAM bandwidth reaches **well under half of datasheet peak**
   (37-45% across runs on this machine). The resource that governs decode is
   the one whose advertised figure is furthest from what you actually get.
2. The measured ridge point is ~25-26 FLOP/byte, so decode is capped at a few
   percent of the machine's peak FLOP/s. The arithmetic units sit idle waiting
   for weights no matter how good the kernel is.

## Decision

**Report TTFT and TPOT separately, against the resource that bounds each.**
Where a single number is unavoidable, report goodput — requests meeting a
latency target — not raw tokens/sec.

Concretely, this repo reports arithmetic intensity and roofline placement per
phase, and never aggregates the two phases into one throughput figure.

## Consequences

### Why a single tokens/sec figure misleads

- **It is a weighted average of two different bottlenecks, and the weight is
  the workload's.** A summarisation workload (long prompts, short outputs) is
  mostly prefill; a chat workload (short prompts, long outputs) is mostly
  decode. The same engine on the same hardware produces very different
  tokens/sec for the two, so the number describes the benchmark's prompt mix as
  much as the system.
- **It hides which resource to spend money on.** Prefill-bound and decode-bound
  systems are improved by opposite purchases: more FLOP/s versus more memory
  bandwidth. A single figure cannot tell you which, and the two are not
  interchangeable.
- **It rewards the wrong optimisations.** Decode sits on the bandwidth roof, so
  a faster matmul kernel changes nothing. What moves decode is reducing bytes
  per token — quantisation, KV cache compression, GQA/MQA — or amortising the
  weight read across more tokens via batching. A tokens/sec headline gives no
  signal about which lever is even available.
- **It obscures the latency the user feels.** TTFT (a prefill property) and
  TPOT (a decode property) are what a user experiences. Their ratio varies
  enormously with prompt length; a throughput average discards it.

### What batching does and does not fix

Batching is the main lever on decode, and this repo quantifies its limit: at
S=1024 a 32x batch raises decode's arithmetic intensity by only ~4.8x, not 32x,
because the KV cache grows with the batch even though the weights do not. It
moves decode *along* the bandwidth roof, not across the ridge. Decode stays
memory-bound at every batch size measured here, on both a DDR5 and an HBM-class
ridge point.

So "just batch it" is a real optimisation with a ceiling, and the ceiling
tightens as context grows. A headline tokens/sec measured at batch 32 and short
context will not survive contact with long-context production traffic.

### Costs of this decision

- Two numbers are harder to communicate than one, and comparison tables want a
  single column. This is a real cost and we accept it.
- TTFT and TPOT both need a specified prompt and output length to be meaningful,
  so reporting them honestly requires publishing the workload shape too.
- Goodput needs an agreed latency target, which is a product decision rather
  than a measurement, and it makes cross-vendor comparison harder.

### What this ADR does not claim

It does not claim tokens/sec is useless. It is a fine *capacity-planning* number
for a fixed workload on fixed hardware, which is exactly the case where the
prompt mix is held constant. The objection is to it as a headline for comparing
systems, where the mix silently varies.

It also does not rest on GPU measurements — this machine has none. The
prefill/decode asymmetry is derived from arithmetic intensity, which depends on
batch size and weight reuse rather than on the memory technology; the DDR5
ridge point measured here and a published HBM ridge point give the same verdict.
The absolute numbers on an accelerator would differ, and this repo does not
establish them.
