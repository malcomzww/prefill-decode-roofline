# Roofline: what holds on any machine

Generated by `python scripts/generate_results.py`. Do not edit by hand.

Absolute GB/s and GFLOP/s live in `results/roofline-raw.md`, which is
gitignored: measured bandwidth is a property of the machine that ran
it, so committing it would make CI fail on a different runner for no
useful reason. The claims below are the portable ones, and this
script asserts each of them and exits non-zero if one breaks.

- Model: gpt2-124M (84.9M transformer
  weights, 2 bytes/param), dimensions analytic --
  no weights downloaded, so nothing here depends on a checkpoint.
- STREAM kernels: add, copy, scale, triad
- Working sets swept: 256 KB to
  128 MB per array
- GEMM sizes: 256, 512, 1024, 2048, 4096 (fp32, seed 0)
- Reproduce: `python scripts/generate_results.py`
- Raw artifact: `results/roofline-raw.md` (gitignored)
- Plot: `results/roofline.png`

## 1. Measured bandwidth falls well short of the datasheet peak

The sustained DRAM-resident bandwidth this machine achieves is **well under half of its datasheet peak** (2 channels x 4.8 GT/s x 8 bytes). That gap is the central measurement of this repo, and it is the normal case rather than a defect:

- The datasheet number assumes zero refresh cycles, zero page-miss
  penalty, and perfect read/write turnaround. Real access patterns pay
  all three.
- STREAM's traffic convention ignores write-allocate: on a store miss
  the cache first *reads* the line it is about to overwrite, so the
  controller moved more bytes than we counted. This makes the figure a
  conservative lower bound.
- A single-socket laptop shares its controller with the display, the
  OS, and every other running process.

The practical lesson: sizing a serving deployment against a datasheet
bandwidth number will overestimate decode throughput by roughly this
factor, and decode is exactly the phase that bandwidth governs.

## 2. Bandwidth depends on where the working set lives

Bandwidth measured with arrays small enough to sit in cache exceeds
what the same kernel sustains once the working set must come from
DRAM. **The size of that gap is a property of the machine, not of the
workload** — it ran 3-5x on a quiet laptop and 1.14x on a shared CI
runner, where a virtualised cache hierarchy flattens it. Only the
direction is asserted here; the magnitude for this run is in the raw
artifact.

This is why the sweep exists: a single-size bandwidth benchmark
reports whichever side of the cliff it happened to land on, and on
real hardware the two differ by more than the entire effect most
optimisations are chasing.

Only DRAM-resident points set the bandwidth roof below. A KV cache at
realistic context lengths does not fit in L3.

## 3. Prefill is compute-bound; decode is memory-bandwidth-bound

At a context of 1024 tokens, batch 1:

| phase | arithmetic intensity | vs ridge point | bound by |
|---|---|---|---|
| prefill | 1024.00 FLOP/byte | above | **compute** |
| decode | 1.00 FLOP/byte | below | **memory** |

Prefill's intensity is **1024x** decode's. The reason is
structural, not incidental: prefill loads each weight once and reuses
it across all 1024 prompt tokens, while decode loads the
entire weight set to produce a single token. Batch-1 decode does two
FLOPs per two-byte weight, which is an arithmetic intensity of ~1 by
construction -- no memory system has a ridge point that low.

## 4. Decode cannot use most of the arithmetic on the machine

The roofline caps decode at **a small fraction** of peak FLOP/s -- the
exact fraction depends on the machine's compute-to-bandwidth ratio and
is in the raw artifact, not committed here. That is not a
kernel-quality problem and no amount of optimisation fixes it: the
point sits on the bandwidth roof, so the arithmetic units are idle
waiting for weights either way.

The direction is what transfers. A machine with a *weaker* compute
roof shows a higher percentage without decode becoming any less
memory-bound -- the ratio moved, not the physics.

This is the argument against tokens/sec as a headline metric --
see `docs/adr/0001-why-tokens-per-second-is-the-wrong-headline.md`.

## 5. The verdict does not depend on this hardware

The prefill/decode split follows from batch size and weight reuse, not
from DDR5. Re-evaluating the same intensities against an HBM-class
roofline moves the ridge point right, which if anything makes decode
*more* memory-bound:

| machine | ridge point | decode verdict | prefill verdict |
|---|---|---|---|
| this machine (DDR5) | ~10s of FLOP/byte | memory-bound | compute-bound |
| HBM-class accelerator | ~100s of FLOP/byte | memory-bound | compute-bound |

The HBM row uses published vendor figures, not measurements taken
here. It is arithmetic on the measured intensities from this repo,
included to show the direction of travel -- not a benchmark result.

## 6. Batching amortises weights, but not the KV cache

A 32x batch raises decode intensity by only **4.8x**, not 32x,
because the KV cache scales with the batch even though the weights do
not. Batching is the main lever on decode efficiency and it is a real
one, but it moves the point *along* the bandwidth roof rather than
across the ridge:

- batch 1 at S=1024: 1.00 FLOP/byte, memory-bound on
  any real memory system
- batch 32 at S=1024: 4.82 FLOP/byte, still far below
  the ridge point of every accelerator in the table above

Whether batch-32 decode crosses a *particular* machine's ridge is
machine-dependent and deliberately not asserted here: on a host with
weak GEMM throughput the ridge can fall below this intensity, which
says more about that host's compute roof than about decode. The CI
runner is exactly such a host, which is how this was found.

The gain is larger at short context, where weight traffic dominates,
and shrinks as the cache grows. That is the tradeoff continuous
batching actually makes.

## Limitations

- **No GPU was measured.** This machine has none. The repo establishes
  where *this* memory system falls short of *its* datasheet peak, and
  that the prefill/decode asymmetry holds against the resulting
  roofline. It does **not** establish the ridge point of any GPU, nor
  what fraction of HBM peak a real accelerator achieves. The HBM row
  in section 5 is arithmetic on vendor figures, not a measurement.
- **Arithmetic intensity is analytic, not profiled.** It is computed
  from layer dimensions, counting dense matmuls and attention products
  and ignoring softmax, layernorm and activations. Those move bytes,
  so the true intensity is slightly *lower* than reported -- which
  strengthens rather than weakens the decode conclusion.
- **No end-to-end inference was run.** No TTFT or TPOT was measured;
  no model weights were downloaded. The claims are about the physics a
  serving engine operates under, not about any engine's implementation.
- **numpy is not a tuned STREAM.** There is no fused multiply-add, so
  `triad` makes two passes and reads lower than `add`. A compiled
  STREAM with non-temporal stores would report a higher peak; the
  measured/theoretical gap here is therefore an upper bound on the gap.
- **Single machine, single run of a sweep.** Reported as the fastest of
  several repetitions, which suppresses scheduler noise but cannot
  remove the influence of whatever else the OS was doing.
